# 知识平台迁移执行计划

## 1. 执行目标

将当前旧版“知识点管理系统”和新版企业知识引擎逐步合并，最终形成唯一的 `knowledge` 知识平台：

```text
knowledge
├── 知识空间
├── 知识点
├── 知识关系与图谱
├── 知识路径
├── 文档与版本
├── 知识点-文档关系
├── Chunk / Embedding / Index
├── 检索与 RAG
└── 审核、任务、审计、备份
```

`education` 只依赖 `knowledge`，维护教育业务本身：

```text
课程、章节、题目、教材、资源、学习状态、复习、能力和计划
```

## 2. 执行原则

### 2.1 先迁移、后删除

禁止直接删除旧 Controller、旧 API 或旧表逻辑。所有旧逻辑都经过：

```text
盘点依赖
→ 新接口实现
→ 兼容转发
→ 调用方迁移
→ 监控观察
→ 删除旧逻辑
```

### 2.2 不改变已有业务 ID

现有教育数据大量引用 `knowledgeId`，第一阶段保留知识点主键和文档主键，避免破坏：

```text
chapter_knowledge
question_knowledge
review
study_record
ability
learning_plan
```

### 2.3 不允许跨空间数据

所有知识点、关系、文档和索引操作必须明确：

```text
tenantId
spaceId
```

知识关系不得跨空间创建，教育调用 knowledge 接口时必须经过空间权限校验。

### 2.4 每个阶段必须可回滚

每个阶段都要满足：

- 数据库迁移可逆或有备份。
- 新旧 API 可以短期并行。
- 前端可以通过开关切换。
- 新逻辑异常时可以回退到兼容层。

## 5. 分阶段执行计划

## 阶段 0：基线、备份和依赖盘点

### 目标

在修改业务逻辑前建立可验证、可回滚的基线。

### 任务

- [ ] 导出当前知识点、关系、文档、文档关系和 Chunk 数据。
- [ ] 备份当前数据库和文件存储。
- [ ] 记录现有接口清单和前端调用方。
- [ ] 统计旧接口调用次数。
- [ ] 为旧接口增加访问日志和弃用标记。
- [ ] 增加知识空间默认空间校验。
- [ ] 补充跨租户、跨空间访问测试。

### 重点检查

```text
KnowledgeRepository 是否按 tenantId / spaceId 查询
KnowledgeRelationRepository 是否按 spaceId 查询
KnowledgeDocumentRepository 是否按 spaceId 查询
教育模块是否直接访问 knowledge DAL
前端是否仍使用旧版页面
```

### 完成条件

- [ ] 有完整数据备份。
- [ ] 有旧接口调用清单。
- [ ] 关键数据可以恢复。
- [ ] 没有未识别的旧逻辑调用方。

## 阶段 1：统一知识空间和核心数据模型

### 目标

让所有知识点和文档都归属明确的知识空间。

### 后端任务

- [ ] 确认每个租户的默认知识空间。
- [ ] 为历史知识点、关系、文档和 Chunk 补齐 `spaceId`。
- [ ] 所有 Repository 增加 `tenantId / spaceId` 条件。
- [ ] 知识点创建接口改为必须指定 `spaceId`。
- [ ] 关系创建校验源节点和目标节点属于同一空间。
- [ ] 文档查询、删除、发布统一校验空间权限。
- [ ] 增加 `difficulty_level` 字段。
- [ ] 增加知识空间难度量表配置。

### 建议模型

```text
knowledge_point.difficulty_level
knowledge_space.difficulty_scale_id
knowledge_difficulty_scale(level, label, description)
```

### 完成条件

- [ ] 所有旧数据都有空间归属。
- [ ] 跨空间关系无法创建。
- [ ] 同一租户不同空间的数据不会互相出现在列表和检索中。
- [ ] 旧接口也经过空间校验。

## 阶段 2：实现新版知识点、关系和路径 API

### 目标

将旧版知识点能力迁移到新版知识平台的空间模型中。

### 新 API

```text

DELETE /knowledge/points/{pointId}
GET    /knowledge/points/{pointId}/relations

DELETE /knowledge/points/{pointId}/relations/{targetId}
GET    /knowledge/points/{pointId}/graph
GET    /knowledge/points/{pointId}/path
GET    /knowledge/points/{pointId}/prerequisites
```

### 代码任务

- [ ] 新增 `KnowledgePointService`。
- [ ] 将 `KnowledgeService` 的知识点 CRUD 逻辑迁入新 Service。
- [ ] 将关系逻辑改造成空间化实现。
- [ ] 将内存图谱的加载、更新和持久化统一。
- [ ] 将 `LearningPathService` 改名为 `KnowledgePathService`。
- [ ] 详情接口拆分知识点、关系和文档，避免一个接口承担所有聚合。
- [ ] 旧 `KnowledgeService` 暂时改为兼容 Facade。

### 完成条件

- [ ] 新 API 能完成知识点 CRUD、关系、图谱和路径闭环。
- [ ] 新旧 API 返回的数据一致。
- [ ] 新 API 通过集成测试。

## 阶段 3：统一文档和知识点-文档关系

### 目标

知识点-文档关系由 knowledge 统一维护，教育不再维护该关系。

### 新 API

```text
GET /knowledge/points/{pointId}/documents
PUT /knowledge/points/{pointId}/documents
```

### 代码任务

- [ ] 新增 `KnowledgeDocumentRelationService`。
- [ ] 将 `DocumentKnowledgeService` 中的关系逻辑迁入新 Service。
- [ ] 兼容旧文档关系接口，但内部转发到新 Service。
- [ ] 统一旧版文本创建和新版文件上传的数据模型。
- [ ] 统一文档版本、解析状态和生命周期状态。
- [ ] 历史文档生成默认版本。
- [ ] 历史文档生成或补建摄取任务。

### 统一文档流程

```text
上传
→ 创建文档版本
→ 创建摄取任务
→ 文件解析
→ Chunk
→ Embedding
→ READY
→ 审核
→ PUBLISHED
→ 空间索引
```

### 完成条件

- [ ] 新旧文档都可以通过新版文档详情查询。
- [ ] 文档关系只有一个写入入口。
- [ ] 文档发布后才进入有效检索索引。
- [ ] 删除文档可以清理版本、Chunk 和向量索引。

## 6. 关键风险与应对

### 6.1 教育数据引用失效

应对：

- 保留已有 `knowledgeId`。
- 不直接删除或重建知识点主键。
- 删除知识点前检查教育侧引用。

### 6.2 新旧索引结果不一致

应对：

- 对同一空间执行双写或双读比对。
- 记录检索结果差异。
- 发布前完成离线重建。

### 6.3 文档状态不一致

应对：

- 统一状态机。
- 文档状态以版本状态为准。
- 发布只允许 `parseStatus = READY`。

### 6.4 空间权限绕过

应对：

- Service 层强制校验空间权限。
- Repository 层强制带租户和空间条件。
- 增加跨租户和跨空间集成测试。

### 6.5 旧接口被外部客户端继续使用

应对：

- 增加弃用日志。
- 提供迁移说明。
