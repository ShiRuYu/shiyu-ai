# 知识平台与教育模块调整方案

## 1. 文档目的

本文档根据当前项目对 `knowledge` 模块和 `education` 模块的分析，明确后续领域边界、目标架构、接口方向和迁移步骤。

配套执行计划：

[知识平台迁移执行计划.md](./知识平台迁移执行计划.md)

本次调整的核心目标：

1. 将 `knowledge` 建设为企业级通用知识平台，而不是仅面向教育的知识点模块。
2. 将旧版“知识点管理系统”能力合并到新版知识引擎。
3. 让 `education` 依赖 `knowledge`，只维护教育业务对知识的使用方式。
4. 消除旧版接口、新版 V2 接口、两套文档处理流程和两套索引体系并存的问题。

## 2. 当前问题概述

当前 `knowledge` 模块同时承载了两类不同职责：

### 2.1 旧版教育知识点体系

- 知识点 CRUD
- 前置、后续和相关关系
- 知识图谱
- 学习路径
- 知识点-文档关联
- 知识点向量搜索
- 教育页面对知识点的选择和展示

主要接口路径：

```text
/knowledge/knowledge/**
/knowledge/document/**
```

### 2.2 新版企业知识引擎体系

- 知识空间
- 空间成员和权限
- 文档上传
- 文档版本
- 文档审核、发布
- 异步解析和摄取任务
- Chunk、Embedding 和混合检索
- 空间索引重建
- 审计、备份和运行状态

主要接口路径：

```text
/knowledge/**
```

### 2.3 主要结构性问题

1. “知识点、知识库、知识空间、文档”概念没有统一。
2. 旧版同步文档摄取流程和新版异步摄取流程并存。
3. 旧版查询没有统一使用 `tenantId` 和 `spaceId` 进行隔离。
4. 旧版和新版各自维护索引重建能力。
5. `KnowledgeService` 同时负责知识点、图谱、文档和搜索聚合。
6. 前端同时存在旧版管理页面、旧版索引页面和新版企业工作台。
7. `education` 通过 `knowledgeId` 使用知识，但知识本体和文档关系仍混在 `knowledge` 旧逻辑中。

## 3. 目标定位

将 `knowledge` 定位为：

> 企业级通用知识平台（Unified Knowledge Platform）

它负责“知识内容本身”和知识内容的生命周期、组织、检索，不限定于教育场景。

目标支持的业务包括：

- 企业内部知识库
- 教育教材和课程知识
- 企业培训
- 产品文档
- 客服知识库
- 法务、医疗等领域知识库

## 5. 关键概念定义

### 5.1 KnowledgeSpace

知识资源的隔离、权限和检索配置边界。

```text
一个租户可以有多个知识空间。
一个知识空间可以包含知识点、文档、版本、Chunk 和索引。
```

### 5.2 KnowledgePoint

结构化知识概念，例如“二次函数”“合同解除”“产品退货政策”。

知识点可以包含：

```text
id
code
name
description
category
tags
spaceId
tenantId
```

`difficultyLevel` 属于所有知识空间都需要的通用能力，应保留在 knowledge 核心模型中；但具体等级数量、名称和说明由知识空间配置，不能写死为教育场景的 1～4 级。

`subject`、`grade` 等字段仍然属于教育语义，应通过教育扩展字段或教育侧关联维护。

建议模型：

```text
knowledge_point
├── difficulty_level
└── ...

knowledge_space
└── difficulty_scale_id

knowledge_difficulty_scale
├── level
├── label
└── description
```

例如：

```text
教育空间：1 初级 / 2 基础 / 3 进阶 / 4 高级
企业培训空间：1 入门 / 2 熟练 / 3 专家
产品文档空间：1 基础 / 2 高级
```

知识点只保存可排序的 `difficulty_level`，展示名称和解释由所属空间的难度量表提供。

### 5.3 KnowledgeDocument

知识来源资产，例如教材、讲义、制度、产品手册和 PDF 文件。

文档具有：

```text
文档
→ 文档版本
→ 解析状态
→ 审核状态
→ 发布状态
→ Chunk
→ Embedding / Index
```

### 5.4 KnowledgeDocumentRelation

表示知识点与文档之间的内容关联：

```text
KnowledgePoint 1 —— N KnowledgeDocument
```

该关系由 `knowledge` 统一维护，教育模块不再维护知识点-文档关系。

## 6. LearningPathService 调整

当前 `LearningPathService` 名称带有明显教育语义，不适合放在企业级通用 knowledge 模块中。

不建议直接改成“知识链路”：

- “链路”容易被理解为数据链路、调用链或文档血缘。
- 不能准确表达前置知识关系生成的路径。
- 后续可能与检索链路、摄取链路产生概念冲突。

### 6.1 推荐改名

优先推荐：

```java
KnowledgePathService
```

如果强调图谱：

```java
KnowledgeGraphPathService
```

如果只处理前置关系：

```java
PrerequisitePathService
```

推荐最终采用：

```java
KnowledgePathService
```

职责定义：

```java
List<Long> generatePath(Long knowledgePointId);

List<Long> findMissingPrerequisites(
        Long knowledgePointId,
        Set<Long> masteredIds);
```

其中：

```text
KnowledgePathService
= 知识结构上的路径计算

education.StudentLearningPathService
= 面向学生的学习计划、进度和任务编排
```

学生掌握状态、复习状态和学习进度仍属于 `education`。

## 7. 目标依赖关系

模块依赖方向统一为：

```text
education  →  knowledge
```

禁止：

```text
knowledge  →  education
```

`education` 只能依赖 `knowledge` 暴露的服务接口或 Facade，不应直接依赖：

```text
KnowledgeRepository
KnowledgeDocumentMapper
KnowledgeChunkRepository
VectorStore
KnowledgeDocumentDO
```

建议暴露以下应用接口：

```java
KnowledgePointQueryService
KnowledgeDocumentQueryService
KnowledgeRelationQueryService
KnowledgeSearchFacade
KnowledgeGraphQueryService
```

## 9. 数据模型调整原则

### 9.1 不立即修改已有 ID

当前教育数据大量保存 `knowledgeId`，包括章节、题目、复习、学习记录和能力数据。

因此第一阶段不改变知识点 ID，避免大规模级联迁移。

### 9.2 统一空间和租户字段

所有知识相关实体必须具备并校验：

```text
tenant_id
space_id
```

关系必须禁止跨空间创建：

```text
KnowledgePoint.source.spaceId
==
KnowledgePoint.target.spaceId
```

### 9.3 表的物理迁移可以后置

可以先保留现有表：

```text
knowledge_base
knowledge_relation
knowledge_document
knowledge_doc_relation
```

先完成：

```text
代码归属调整
Service 调整
API 调整
权限和空间隔离
```

确认稳定后，再考虑重命名为更清晰的表名。

## 10. 迁移实施阶段

### 阶段一：确定新版为唯一主模型

- 停止新增旧版 knowledge API。
- 保持 `/knowledge/**` 为唯一正式接口，不引入 URL 版本兼容层。
- 明确 `KnowledgeSpace` 为顶层边界。
- 补齐所有接口的 `spaceId` 和租户隔离。

### 阶段二：合并旧版知识点能力

- 将 `KnowledgeService` 改造为 `KnowledgePointService`。
- 将 `KnowledgeRelationService` 纳入新版空间模型。
- 将 `KnowledgeGraph` 改造为持久化、空间隔离的图谱能力。
- 将 `LearningPathService` 改名为 `KnowledgePathService`。
- 将知识点-文档关系统一交给 knowledge。

### 阶段三：统一文档摄取流程

统一为：

```text
上传
→ 版本
→ 异步摄取任务
→ 文档解析
→ Chunk
→ Embedding
→ 审核
→ 发布
→ 空间索引
```

废弃旧版同步调用：

```java
DocumentKnowledgeService.create(...)
ingestionService.ingest(...)
```

旧数据可以通过迁移任务生成默认版本和摄取任务。

### 阶段四：education 改为依赖 knowledge

- 删除 education 对 knowledge DAL 层的直接依赖。
- 通过 knowledge Service / Facade 查询知识点和文档。
- 保留章节、题目、教材、资源等教育关系。
- 教育侧只维护学生学习状态和教育场景关系。

### 阶段五：前端收敛

新版前端建议拆分为：

```text
知识空间
知识点
文档中心
知识图谱
检索测试
摄取任务
索引管理
审计与运维
```

不再同时维护旧版知识点页面和新版企业工作台两套入口。

## 11. 验收标准

### 领域边界

- [ ] knowledge 不依赖 education。
- [ ] education 不直接访问 knowledge DAL。
- [ ] 知识点-文档关系只有 knowledge 一个维护方。
- [ ] 学生学习状态只有 education 一个维护方。

### 数据隔离

- [ ] 所有知识点查询带租户和空间边界。
- [ ] 所有文档查询带空间权限。
- [ ] 关系不能跨空间创建。
- [ ] 删除和发布操作完成权限校验。

### 流程一致性

- [ ] 新旧文档统一使用异步摄取流程。
- [ ] 只有一套正式索引重建接口。
- [ ] 文档版本、解析状态、生命周期状态含义统一。
- [ ] 发布后只将已发布版本纳入有效检索索引。

### 前端一致性

- [ ] 旧版 API 页面不再作为主入口。
- [ ] 文档上传、审核、版本、回滚流程可闭环。
- [ ] 知识点、关系、图谱均按空间加载。
- [ ] 任务列表支持分页和状态刷新。

## 12. 最终结论

最终采用以下定位：

```text
knowledge
= 企业级通用知识平台
= 知识空间 + 知识点 + 难度体系 + 文档 + 图谱 + 检索 + RAG

education
= 教育业务平台
= 课程、章节、题目、学习、复习、能力和计划
```

最终核心原则：

> knowledge 负责定义和管理知识，education 负责在教育场景中使用知识。

`LearningPathService` 不建议改为“知识链路”，建议改名为：

```text
KnowledgePathService
```

表示通用知识结构路径；学生学习计划则由 `education` 另行实现。
