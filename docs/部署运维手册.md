# 部署与运维手册

## 运行基线

- JDK：21。项目可在更高版本 JDK 上构建，但通过 `--release 21` 保证产物 API 基线。
- Maven：3.9+。
- 默认端口：9000。
- 默认数据：`${APP_HOME}/data`，包括 H2、文件、索引、向量、备份和运行数据。
- 默认数据库：H2 File/MVStore，`AUTO_SERVER=FALSE`，属于单写实例部署。

## 构建与启动

```powershell
mvn clean test
mvn -pl infrastructure/shiyu-ai-bootstrap -am package '-Dmaven.test.skip=true'
$env:APP_HOME='D:\shiyu-runtime'
java -jar infrastructure\shiyu-ai-bootstrap\target\shiyu-ai-bootstrap-1.0.0.jar --server.port=9000
```

生产环境应以服务账户运行，`APP_HOME` 使用独立持久卷，并限制目录权限。不要直接以源码目录作为生产数据目录。

## 反向代理要点

- `/api/*` 是前端开发代理前缀，后端原生接口没有 `/api`；生产代理应剥离 `/api`。
- SSE/流式接口关闭代理缓冲，增加读取超时并保持连接。
- 上传限制需同时满足网关、Spring multipart 和存储安全限制；当前单文件有效上限受 Spring 50 MB 限制，存储层上限 200 MB。
- 强制 HTTPS，并转发 `X-Forwarded-*` 头。

Nginx 示例片段：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:9000/;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 300s;
    proxy_buffering off;
}
```

## 配置与容量

关键环境变量包括 `APP_HOME`、`SHIYU_STORAGE_TYPE`、各对象存储凭证，以及模型供应商密钥。CORS 可通过 `shiyu.web.cors.allowed-origin-patterns` 指定逗号分隔来源。

容量至少估算：数据库增长 + 原始文件 + 模型/索引 + 向量数据 + 20 GB 默认备份上限 + 2 GB 默认日志上限 + 30% 临时空间。H2 文件模式不适合多实例共享同一数据库文件；需要水平扩展时应先完成外部数据库、分布式缓存/会话和共享对象存储改造。

## 备份与恢复

系统默认每小时执行一次一致性备份，首次延迟 5 分钟；保留最近 24 份小时快照、30 个日快照，总量上限 20 GB。快照包含：

- `database/h2-backup.zip`
- `files/`
- `models/`
- `index/`
- `manifest.properties`

默认 RPO 约为一个备份周期；RTO 取决于数据量和恢复演练。恢复步骤：

1. 停止应用并复制当前 `APP_HOME/data` 到隔离位置。
2. 对目标快照调用系统的 restore-check 能力或离线检查 ZIP，确认数据库和 manifest 存在且可完整读取。
3. 解压快照；使用与运行时相同版本的 H2 `org.h2.tools.Restore` 将 `database/h2-backup.zip` 恢复到新的 `data/db`。
4. 恢复 `files`、`models`、`index`；向量目录若未包含或版本不匹配，按知识库任务重新构建。
5. 用新的临时 `APP_HOME` 启动，验证登录、权限、菜单、知识检索和文件下载后再切换流量。

必须定期做异机恢复演练；“备份任务成功”不等于“可恢复”。

## 监控与巡检

每次发布检查：进程存活、端口、磁盘可用量、最近备份时间、错误日志、Hikari 连接、AI 调用错误率与延迟、SSE 断开率、知识任务积压。数据保留默认：运行日志 30 天/2 GB，执行记录 30 天，审计 180 天，用量 365 天，任务 30 天。

## 发布与回滚

1. 运行后端测试、前端类型/单测/构建、接口契约测试。
2. 创建并校验发布前备份。
3. 保存旧 jar、配置摘要和前端静态包。
4. 在新 `APP_HOME` 或预发布环境进行冒烟测试。
5. 停机替换并启动；检查登录、菜单、核心读写、SSE、上传下载。
6. 回滚时恢复旧 jar；若发生不可逆数据变更，同时执行已经演练的数据恢复方案。

数据库 baseline 采用一次性最终值策略，不提供启动期增量迁移。发布若改变 baseline 版本，必须在停机窗口先备份，使用新目录完成空库初始化及必要的数据导入验证，再切换流量；不要通过临时 UPDATE 脚本把旧库伪装成新版本。
