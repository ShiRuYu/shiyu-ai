# 模块结构与命名约定

后端采用“职责分组目录 + Maven 叶子模块”的结构。分组目录用于帮助开发者按架构层次浏览，叶子目录才是可独立构建、发布和被依赖的 Maven 模块。

## 目录层次

```text
modules/
├── applications/       # 可运行应用和组合根
│   └── shiyu-ai-web/   # Web 入口、装配和运行配置
├── domains/            # 业务领域
│   └── <domain>/
│       ├── shiyu-<domain>-contract/
│       └── shiyu-<domain>-implementation/
└── infrastructure/     # 可复用的技术基础设施
    ├── shiyu-common-<capability>/
    │   ├── config/       # provider 属性与条件化 Bean
    │   ├── adapter/      # 外部设施适配器
    │   ├── provider/     # provider 选择和工厂
    │   └── metadata/     # 外部资源元数据
    └── ...
```

`applications`、`domains` 和 `infrastructure` 是组织目录，不需要为每个组织目录新增 `pom.xml`。根 POM 直接聚合叶子模块，避免增加没有独立依赖边界的空聚合层。

## 命名规则

- Maven `artifactId` 使用 `shiyu-<职责>` 或 `shiyu-<domain>-<role>`，全部使用小写和连字符。
- Java 包名使用 `com.shiyu.ai.<领域或能力>`，与 Maven 坐标保持语义一致，不把目录名称直接当作 Java 包名。
- 领域模块优先拆成 `contract` 和 `implementation`：前者只放稳定接口、模型和跨模块契约，后者放应用服务、持久化、适配器和运行实现。
- 基础设施模块以实际能力命名，例如 `shiyu-common-core`、`shiyu-common-mybatis`、`shiyu-common-storage`；不要使用含义过宽的 `misc`、`utils` 或 `common-impl`。
- 目录重命名必须同步检查根 POM、模块依赖、IDE 配置、脚本和文档引用；Maven 坐标或 Java 包名只有在确有兼容迁移计划时才调整。provider 适配器放在现有基础设施叶子模块中，不新增服务进程或独立 Maven 模块。

## 放置规则

新增代码先按职责判断：启动类、组合根和跨领域装配放在 `applications`；业务 Controller 与业务规则、领域端口放在对应 `domains/<domain>-implementation`；可复用的 HTTP 异常、过滤器、数据库、线程、存储、Redis、向量和事件技术实现放在 `infrastructure`。provider 配置集中在 `config`，外部系统调用放在 `adapter`，选择逻辑放在 `provider`，数据库/对象元数据放在 `metadata`。技术模块可以拥有自己的健康检查或文件控制器，但不得承载领域业务规则。跨领域共享代码只有在依赖稳定、职责明确时才进入基础设施，避免把共享目录变成临时文件收容处。

模块调整后至少执行一次 `mvn -q -DskipTests compile`，并检查 `git grep` 是否仍引用旧路径；涉及行为变化时再运行对应模块测试或完整测试。
